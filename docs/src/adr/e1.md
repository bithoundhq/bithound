# ADR-E1 — LND-domain state and kinds for V0.8

**Date.** 2026-05-23.
**Status.** Accepted.
**Scope.** Per-channel state variant plus the incident-kind registry
entries required for V0.8 LND rules (B1 channel inactive, B6
chain-backend lag). Establishes the E cluster (Lightning-domain
modelling).

**Context.** V0 already shipped substantial LND entity scaffolding:

- LND identifier newtypes (`LndNodeId`, `LndPeerId`, `LndChannelId`,
  `LndInvoiceId`) in `src/shared/types.rs`.
- `EntityRef::{LndNode, LndPeer, LndChannel, LndInvoice}` variants
  with sub-entity scoping per ADR-N1 (peer / channel / invoice IDs
  scoped under their parent `LndNodeId`).
- `EntitySubjectKind` discriminants for all four LND variants.
- `StateObservation::{LndNode, LndWallet, LndChannelSummary}` variants
  with structs covering `getinfo`, wallet balances, and aggregate
  channel counts.
- `well_known::{LND_NODE, LND_WALLET, LND_CHANNEL_SUMMARY}` state
  name constants in `src/observations/types/state/well_known.rs`.

V0.8 LND rules (B1 channel inactive, B6 chain-backend lag, per the
amended V1 design doc and `docs/INCIDENT_CATALOG.md` §§ B1, B6) need
additional surface the V0 codebase doesn't yet provide:

1. `LndChannelSummaryState` is aggregate (`active_channels: u64`,
   `inactive_channels: u64`, ...). The B1 rule fires per channel and
   needs per-channel `.active` plus identifying fields.
2. B6 (`lnd.chain_backend_lag` — LND's view of the chain tip vs
   bitcoind's, per the catalog) is a **cross-source correlation
   rule** reading two existing state observations. It requires no
   new state variant; only the incident-kind registry entry needs to
   land.
3. The incident-kind constants `lnd.channel_inactive` and
   `lnd.chain_backend_lag` don't exist in
   `src/incidents/well_known.rs::ALL` (only the three Bitcoin V0 kinds
   are there). Their `default_kinds.toml` entries are also missing.

A note on terminology: "watchtower" in the LND ecosystem refers
ambiguously to (a) the **wtclient breach-monitoring service** a
client LND connects to for backup channel-state, and (b) **LND's
chain-backend watching role** (LND keeping up with bitcoind's tip).
INCIDENT_CATALOG.md § B6 uses sense (b); this ADR follows that
naming. Sense (a) — wtclient session observability — is a separate
concern handled in a future ADR when demand emerges.

This ADR closes those gaps. It's intentionally narrow: the LND entity
domain is already largely there; what's missing is the per-instance
state surface and the registry entries.

**Decision.**

### E1.0 — E cluster scope

The E cluster covers **Lightning-domain modelling**. This ADR
establishes the cluster for LND specifically; future Lightning
implementations (CLN, Eclair) and Lightning-adjacent observability
work (LSP integrations, watchtower-as-server) land here too.

Bitcoin-extension chains (Elements / Liquid) are explicitly **out of
scope** for the E cluster; they'd get their own letter when needed,
because Bitcoin-extension state and Lightning state are unrelated
domains and bundling them under one cluster would lose locality.

### E1.1 — Per-channel state: `StateObservation::LndChannel(LndChannelState)`

```rust
// src/observations/types/state.rs

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct LndChannelState {
    /// 33-byte secp256k1 pubkey of the remote node, hex-encoded.
    pub remote_pubkey: String,
    pub capacity_sat: u64,
    pub local_balance_sat: u64,
    pub remote_balance_sat: u64,
    /// Mirror of LND's `lnrpc.Channel.active` — `true` when the
    /// channel is currently usable for routing. The B1 rule reads
    /// this field as-is; no re-derivation.
    pub active: bool,
    pub private: bool,
    pub initiator: bool,
    pub csv_delay: u32,
    pub commit_fee_sat: u64,
    /// Seconds since channel open.
    pub lifetime_seconds: u64,
    /// Block height at which LND last observed the channel update
    /// gossip. `None` for brand-new channels with no updates yet.
    pub last_update_height: Option<u64>,
    /// Short-channel-id once the funding tx is confirmed enough for
    /// gossip propagation (LND populates this in `lnrpc.Channel.chan_id`
    /// after ~6 confirmations). `None` for pending or unannounced
    /// channels. This field is informational; channel identity uses
    /// `LndChannelId` (the funding outpoint), not the SCID.
    pub short_channel_id: Option<String>,
    /// Derived at poll time by cross-referencing the channel's
    /// `remote_pubkey` against the same poll tick's `ListPeers`
    /// response (collector pattern specified in ADR-E2 § E2.5).
    /// `Some(true)` means the peer was connected during this poll;
    /// `Some(false)` means it wasn't; `None` means the cross-reference
    /// couldn't be made (e.g. `ListPeers` failed while `ListChannels`
    /// succeeded, so the channel observation lands as a partial in
    /// `ProbeResult::Failed.partial_observations`). The B1 rule uses
    /// this to distinguish "channel inactive because peer offline"
    /// (routine) from "channel inactive while peer is online"
    /// (suspicious).
    pub peer_online: Option<bool>,
}
```

**Channel identity is the funding outpoint for the channel's whole
lifecycle.** `LndChannelId` wraps the string form `"txid:vout"` and
is stable from pending through confirmed through closed. The
short-channel-id (LND's `lnrpc.Channel.chan_id`, populated only after
gossip-eligible confirmation depth) is *not* the identity — it's a
secondary field carried in `LndChannelState.short_channel_id`.

Why: SCID isn't set on a pending channel and changes form between
`pending → confirmed` in LND's API. Using it as identity would mean a
channel's `EntityRef` mutates mid-lifecycle, which breaks incident
dedup (a B1 incident opened on the pending form would not match a
state update emitted under the confirmed form). The funding outpoint
is immutable from the channel's first observable state through close,
so it's the only valid identity choice.

Add to `StateObservation`:

```rust
pub enum StateObservation {
    BitcoinBlockchain(BitcoinBlockchainState),
    BitcoinMempool(BitcoinMempoolState),
    BitcoinNetwork(BitcoinNetworkState),
    BitcoinPeerSummary(BitcoinPeerSummaryState),

    LndNode(LndNodeState),
    LndWallet(LndWalletState),
    LndChannelSummary(LndChannelSummaryState),
    LndChannel(LndChannelState),                    // NEW

    Host(HostState),
}
```

`StateObservation::name()` arm:

```rust
Self::LndChannel(_) => well_known::LND_CHANNEL_DETAIL,
```

**Subject of a `LndChannel` state observation is
`EntityRef::LndChannel { node_id, channel_id }`** — the existing
sub-entity scoping from ADR-N1 handles cross-node uniqueness.

### E1.2 — B6 (`lnd.chain_backend_lag`) needs no new state variant

The B6 rule reads two **existing** state observations and emits an
incident signal when they diverge:

- `LndNodeState.block_height` — from the V0.8 LND polling collector
  (LND's view of the chain tip).
- `BitcoinBlockchainState.blocks` — from V0's
  `BitcoinCoreRpcCollector` (bitcoind's view of the chain tip).

Both already exist. The rule is a cross-source correlation that lives
in the rule layer, not the type system. **No new state variant. No
new `EntityRef` variant.** This is the lightest possible
implementation of B6.

### E1.3 — B6 fingerprint and correlation rule shape

The `lnd.chain_backend_lag` rule fingerprint:

```text
subject:   EntityRef::LndNode(node_id)
kind:      lnd.chain_backend_lag
dimension: None
```

Detection logic (lives in the rule, illustrative):

```text
let lnd_height = state_read.latest_state(
    EntityRef::LndNode(node_id),
    StateName::from_well_known(LND_NODE),
)?.block_height;

let bitcoind_height = state_read.latest_state(
    EntityRef::BitcoinNode(bitcoind_id),
    StateName::from_well_known(BITCOIN_BLOCKCHAIN),
)?.blocks;

let lag = bitcoind_height.saturating_sub(lnd_height);
if lag > lag_blocks_threshold {
    // persisted for lag_persist_seconds → emit Active draft
}
```

Default thresholds (per V0.8 rule config):
- `lag_blocks_threshold = 2` blocks
- `lag_persist_seconds = 60` (one block interval, generous; catches
  real lag, ignores per-block race conditions)

**V0.8 correlation policy.** The rule assumes the sidecar monitors
one LND node correlated against one bitcoind node (the typical
deployment). If the sidecar config has multiple `BitcoinNodeId`s the
rule operator must pick one via collector config
(`[collectors.lnd.nodes.<id>].chain_backend_target_bitcoind_id`).
Per E1.5 below, `allows_dimension = false` for V0.8; the correlation
target is resolved at rule-construction time, not at draft-emission
time.
v1.x revisits if multi-correlation matters.

**Future expansion path.** If a rule emerges that needs per-(LND-node,
bitcoind-node) pair fingerprinting (e.g. "this LND-bitcoind pair
specifically is lagged, the other pairs aren't"), promote the
correlation target to either `dimension = Some(bitcoind_id)` or to a
new `EntityRef::LndChainBackend { lnd_node_id, bitcoind_id }`
sub-entity variant. Either is reversible from the current shape.

**On wtclient watchtower-session observability** (sense (a) of
"watchtower" — the breach-monitoring service): not in V0.8 scope.
When demand emerges, a follow-on ADR specifies the wtclient state
shape, fingerprint, and an `lnd.wtclient_session_lag` rule. Most
likely fingerprint then: `subject = LndNode(node_id)`, `dimension =
Some(tower_pubkey)`, since tower pubkeys are globally unique and the
relationship being monitored is per-(client, tower) — but that's a
future ADR's call.

### E1.4 — Incident-kind well-known constants

```rust
// src/incidents/well_known.rs

pub const BITCOIN_RPC_UNREACHABLE: &str = "bitcoin.rpc_unreachable";
pub const BITCOIN_NO_PEERS: &str = "bitcoin.no_peers";
pub const BITCOIN_TIP_LAG_OR_IBD_STALLED: &str = "bitcoin.tip_lag_or_ibd_stalled";
pub const LND_CHANNEL_INACTIVE: &str = "lnd.channel_inactive";       // NEW
pub const LND_CHAIN_BACKEND_LAG: &str = "lnd.chain_backend_lag";     // NEW

pub const ALL: &[&str] = &[
    BITCOIN_RPC_UNREACHABLE,
    BITCOIN_NO_PEERS,
    BITCOIN_TIP_LAG_OR_IBD_STALLED,
    LND_CHANNEL_INACTIVE,                                            // NEW
    LND_CHAIN_BACKEND_LAG,                                           // NEW
];
```

Parallel state-name constant in
`src/observations/types/state/well_known.rs`:

```rust
pub const LND_NODE: &str = "lnd.node";
pub const LND_WALLET: &str = "lnd.wallet";
pub const LND_CHANNEL_SUMMARY: &str = "lnd.channel_summary";
pub const LND_CHANNEL_DETAIL: &str = "lnd.channel_detail";           // NEW

pub const ALL: &[&str] = &[
    // ...existing...
    LND_CHANNEL_DETAIL,                                              // NEW
];
```

`LND_CHANNEL_DETAIL` ("lnd.channel_detail") rather than the obvious
`"lnd.channel"` because `lnd.channel_summary` already exists for the
aggregate state; `*_detail` makes per-instance vs aggregate explicit
to anyone reading the state-name catalog cold.

**Parity tests cover both directions.** The existing
`state.rs::parity_variants_match_well_known` test asserts every
`StateObservation` variant has a matching `state::well_known::ALL`
entry (variants → constants). The
`well_known.rs::embedded_default_kinds_match_well_known_constants`
test asserts every constant in `incidents/well_known.rs::ALL` is
present in `default_kinds.toml` (constants → TOML). The reverse
direction (TOML → constants) is also worth a guard: a new ticket
should add an `embedded_default_kinds_subset_of_well_known_constants`
test (or fold both checks into a single bidirectional assertion) so a
contributor adding a TOML entry without updating `ALL` fails the
build too.

### E1.5 — `default_kinds.toml` entries

```toml
[[kinds]]
name = "lnd.channel_inactive"
allowed_subjects = ["LndChannel"]
allows_dimension = false
min_open_confidence = "Medium"

[[kinds]]
name = "lnd.chain_backend_lag"
allowed_subjects = ["LndNode"]
allows_dimension = false
min_open_confidence = "High"
```

**`min_open_confidence = "Medium"` for `lnd.channel_inactive`**:
channels flap when peers disconnect briefly, and the V0.8 rule has
hysteresis (default 5 minutes for non-private, 30 minutes for private)
before lifting. Medium acknowledges the residual false-positive class
that high-confidence wouldn't tolerate.

**`min_open_confidence = "High"` for `lnd.chain_backend_lag`**:
chain-backend lag is unambiguous — the rule reads two existing state
observations and the height difference is a deterministic integer.
With `lag_persist_seconds = 60` covering single-block races, no
ambiguity remains worth a confidence haircut.

**On `min_open_confidence` provenance.** This field is currently in
`default_kinds.toml` for the three V0 Bitcoin kinds but isn't
documented in ADR-L1 (which defines `IncidentKindSpec` as `name /
allowed_subjects / allows_dimension / dimension_label / source`). The
field exists in the codebase; an amendment to ADR-L1 to document it
formally is a small follow-on. Not blocking V0.8.

### E1.6 — Smart-constructor migration for LND identifiers (deferred)

`LndNodeId`, `LndPeerId`, `LndChannelId`, `LndInvoiceId` remain
`pub struct X(pub String)` in V0.8. They're NOT dotted-name shaped
so ADR-D2's `parse_dotted_name` parser doesn't apply; they each have
their own LND-specific format:

- `LndNodeId`, `LndPeerId`: 66-char lowercase hex (33-byte secp256k1
  pubkey)
- `LndChannelId`: SCID-form (`block:txindex:output`) once confirmed,
  funding-outpoint form (`txid:vout`) for pending
- `LndInvoiceId`: payment hash, 64-char lowercase hex

Validation at the collector boundary is acceptable for V0.8 (the LND
gRPC API doesn't return malformed identifiers for non-malicious nodes).
Smart constructors land in a follow-on ADR (likely D5 or E4) when:

- A V0.x ticket adds a code path that constructs these identifiers
  from operator config or external API responses, or
- Schema migration removes the `pub` field across the codebase.

Deferring keeps E1's scope tight on the V0.8 rule needs.

**Schema impact (ADR-P1).** No SQLite migration is required for V0.8.
`subject_kind = "lnd_channel"` already exists in the schema (ADR-N1
landed it); the new state name `lnd.channel_detail` is just a string
value in the existing observations table. `subject_kind = "lnd_node"`
is also already present, so `lnd.chain_backend_lag` incidents store
in existing rows. The first SQLite migration of V0.8 (if any) lands
with the V1.0 LND subscription work, not here.

**Rationale.**

- **Phase D already shipped the bulk of LND entity work**, so this
  ADR is small by design. Resisting the temptation to retro-fit
  unrelated concerns (smart constructors, EntityRef expansion,
  read-model schema) keeps it landable in one PR.
- **Per-channel state as its own `StateObservation` variant** matches
  how V0 modelled Bitcoin: per-subsystem state observations keyed by
  `(subject, name)`. The B1 rule then reads via the existing
  `StateReadModel::latest_state(EntityRef::LndChannel{..}, "lnd.channel_detail")`
  path with no new read-model surface.
- **Funding outpoint as channel identity** is the only choice that
  survives the channel's full lifecycle. SCID changes on confirmation
  and isn't set on pending channels; using it as identity would mean
  the same channel's `EntityRef` mutates mid-life and breaks dedup.
- **B6 as a cross-source correlation rule with no new state variant.**
  The data already exists in `LndNodeState` and `BitcoinBlockchainState`;
  the rule joins them. Adding state-tree surface to model something
  the rule layer already handles cleanly would be premature.
- **Confidence asymmetry between B1 and B6** reflects underlying
  signal quality. Channel state flaps under brief peer disconnects;
  chain-backend lag is a deterministic integer comparison.

**Alternatives considered.**

- **Extend `LndChannelSummaryState` to carry a `Vec<PerChannelEntry>`**
  rather than adding a new `LndChannel` variant. Rejected because it
  conflates aggregate state (counts) with per-instance state (per
  channel), and `StateReadModel::latest_state(subject, name)` would
  have to be re-keyed: a single summary observation would need to
  fan out to many channel subjects, breaking the
  one-observation-one-subject contract.
- **Use SCID (`lnrpc.Channel.chan_id`) as `LndChannelId`** when
  available, falling back to funding outpoint for pending. Rejected
  per E1.1 — identity must be stable across the channel's whole life
  or incident dedup breaks at the pending→confirmed boundary.
- **Add a new `LndWatchtowerState` for the B6 rule** (the original
  draft of this ADR). Rejected once it became clear `INCIDENT_CATALOG.md`
  § B6 is about **chain-backend** lag (LND vs bitcoind tip), not
  wtclient session lag. The catalog's "watchtower" terminology was
  ambiguous; the catalog's actual signals make the semantics
  unambiguous. wtclient observability is a separate concern with its
  own future ADR.
- **`lnd.channel` as the per-instance state name.** Rejected because
  `lnd.channel_summary` already exists for aggregate counts; reading
  the two side-by-side in a catalog without `_detail` suffix invites
  confusion. The cost of the longer name is zero; the cost of the
  ambiguity is a future bug report.
- **Smart-constructor migration for LND identifiers in this ADR.**
  Rejected per E1.6 — the migration is its own coherent ADR (different
  parsers per identifier type, different validation windows, different
  deferred-validation strategies), and folding it into the V0.8
  enablement ADR muddies both.
- **`min_open_confidence = "High"` for `lnd.channel_inactive`** to
  match Bitcoin V0 rules. Rejected — channels flap legitimately
  (peer brief disconnects) and a high-confidence bar would force
  longer hysteresis windows that delay legitimate incidents.

**Open follow-ons (do not block v0.8 tickets).**

- **ADR-E2 — LND polling collector patterns.** Defines the gRPC +
  macaroon + TLS client foundation, RPC surface per polling tick,
  per-RPC timeout pattern, error mapping. Required before any v0.8
  collector ticket.
- **ADR-D5 / ADR-E4 — Smart-constructor migration for LND
  identifiers.** Per-type parsers and validation. Deferred per E1.6.
- **ADR-E3 — LND subscription patterns** (v1.0). Stream reconnect +
  reconcile contract. Out of scope for v0.8.
- **Future ADR — wtclient watchtower-session observability.** If a
  rule emerges for the "is my breach-monitoring tower healthy"
  question (sense (a) of "watchtower"), specifies the wtclient state
  variant, fingerprint dimensions, and corresponding rule. Not in
  V0.8 scope.
- **Bidirectional parity test for `default_kinds.toml` ↔
  `well_known::ALL`.** Small ticket alongside the v0.8 collector
  work — adds a test that fails the build if either side has an
  entry the other lacks.
