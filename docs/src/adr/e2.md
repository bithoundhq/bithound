# ADR-E2 — LND polling collector patterns

**Date.** 2026-05-23.
**Status.** Accepted.
**Scope.** The implementation contract for `LndGrpcPollingCollector`
— the first concrete gRPC-based `PollingCollector` in the codebase
and the gate before v0.8 LND tickets can start.

**Context.** V0 has no gRPC client. ADR-C3 § C3.3 stubbed
`src/collectors/lnd/` but never specified the collector pattern.
ADR-E1 defined the LND state and incident-kind surface; the rules
that consume that surface (B1 channel inactive, B6 chain-backend
lag, per the amended V1 design doc) need a polling collector to
produce the observations they read.

The Bitcoin collector pattern (ADR-C3 § C3.2 + § C3.8) is the
analog to mirror: thin RPC-client wrapper + free-constructor
collector + per-RPC timeout + health observations. Three things
make LND meaningfully different:

1. **gRPC + protobuf** instead of JSON-RPC. New build-time dependency
   on `tonic-build`; new runtime dependencies on `tonic` and `prost`.
2. **Per-node TLS roots and per-node macaroons.** A `tonic::Channel`
   can't be shared across LND nodes the way `reqwest::Client` is
   shared across Bitcoin nodes (per ADR-C3 § C3.6). One channel
   per LND node.
3. **LND's self-signed cert.** Trust must come from the configured
   cert file, not from native OS roots.

**Decision.**

### E2.1 — Module layout

```
src/collectors/lnd/
├── mod.rs                # re-exports
├── grpc_poll.rs          # LndGrpcPollingCollector + impl PollingCollector
├── grpc_client.rs        # LndGrpcClient (thin tonic wrapper)
└── proto/
    ├── README.md         # pinned LND version, source URL, update cadence
    └── lightning.proto   # vendored from LND's lnrpc/, pinned version
```

`src/collectors/mod.rs` adds `pub mod lnd;` alongside the existing
`pub mod bitcoin_core;`.

A `build.rs` at the repo root invokes `tonic-build` over the
vendored proto files. The generated Rust code lands in `OUT_DIR` and
is included via `tonic::include_proto!("lnrpc")` from `grpc_client.rs`.

**Supersedes ADR-C3 § C3.3's `src/collectors/lnd/` layout sketch.**
C3.3 listed `grpc_poll.rs`, `grpc_stream.rs`, and `rest.rs` as the
LND module structure. This ADR keeps `grpc_poll.rs`, defers
`grpc_stream.rs` to ADR-E3 (V1.0 subscription work), and drops
`rest.rs` indefinitely — LND's REST API is a deprecated transport
that lacks coverage of newer subscription endpoints, and the gRPC
client carries us through V1.x without a REST detour.

### E2.2 — Proto file management

LND publishes its `.proto` files under `lnrpc/` in the
`lightningnetwork/lnd` repo. Vendor them at a pinned version
(initial target: LND **v0.18.5-beta**, the latest stable as of
2026-05-23) under `src/collectors/lnd/proto/`.

`proto/README.md` documents:

- The pinned LND version (`vX.Y.Z-beta`).
- The source URL (e.g.
  `https://github.com/lightningnetwork/lnd/tree/v0.18.5-beta/lnrpc`).
- Which `.proto` files are vendored (v0.8 needs `lightning.proto`
  only; `walletunlocker.proto` / `signrpc/` / `walletrpc/` etc. wait
  for V1.0 subscription work or later sub-services).
- The update cadence: review the diff on each new LND minor release
  (every 3-6 months); land any new fields the v0.8 collector needs;
  do NOT auto-update — pin movement is a deliberate decision.

Build dependencies added to `Cargo.toml`:

```toml
[build-dependencies]
tonic-build = "0.12"
```

Runtime dependencies added:

```toml
[dependencies]
tonic = { version = "0.12", features = ["tls"] }
prost = "0.13"
rustls-pemfile = "2"
```

The `tls` feature is additive on top of tonic's defaults
(`transport`, `codegen`, `prost`), so we don't disable defaults and
risk dropping a feature the generated code expects. `tls` pulls in
`rustls` (matches the codebase's existing `sqlx` TLS choice). The
`tls-roots` and `tls-webpki-roots` features are deliberately NOT
enabled (per E2.6 — we want LND-cert-only trust, not native roots).

`build.rs` at the repo root:

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Re-run codegen only when the proto file changes (not on
    // every cargo invocation).
    println!("cargo:rerun-if-changed=src/collectors/lnd/proto/lightning.proto");

    tonic_build::configure()
        .build_server(false)
        .build_client(true)
        .compile_protos(
            &["src/collectors/lnd/proto/lightning.proto"],
            &["src/collectors/lnd/proto"],
        )?;
    Ok(())
}
```

`build_server(false)` because Bithound never serves the LND API; it
only consumes it. `build_client(true)` is the default but worth
naming for clarity.

**Transitive proto dependencies (real implementation risk).** LND's
`lightning.proto` imports supporting protos — notably
`google/api/annotations.proto` (for the REST gateway annotations),
which itself imports `google/api/http.proto` and a handful of
sub-service imports. The vendor step must chase these transitively;
the typical vendored set is 3–5 supporting files in
`src/collectors/lnd/proto/google/api/`. The alternative — strip the
`option (google.api.http) = { ... }` annotations from a local copy
of `lightning.proto` — is cheaper to vendor but creates drift from
upstream. The first vendor PR confirms which approach lands; default
to vendoring the full annotation set unless proven painful. **Treat
the proto vendor task as a 2-3 day item, not a one-file copy.**

### E2.3 — `LndGrpcClient` shape

One `LndGrpcClient` per LND node, owning a pre-built
`tonic::transport::Channel`, the macaroon, and the per-RPC timeout.
The collector consumes the existing `LndNodeConnection` in
`src/collectors/registry.rs` (the macaroon is already resolved to a
`SecretString` value at config-load time per ADR-X1; only the TLS
cert is read from disk at collector construction):

```rust
// src/collectors/lnd/grpc_client.rs

use std::time::Duration;
use secrecy::SecretString;

pub struct LndGrpcClient {
    channel: tonic::transport::Channel,
    /// Macaroon hex-encoded; stamped on every request as the
    /// `macaroon` metadata header (per E2.7). Hex derivation happens
    /// once at construction; the raw bytes never re-cross task
    /// boundaries.
    macaroon_hex: String,
    timeout: Duration,
}

#[derive(Debug, thiserror::Error)]
pub enum BuildError {
    #[error("cannot read TLS cert at {path}: {source}")]
    TlsCertRead { path: String, source: std::io::Error },
    #[error("invalid TLS cert PEM at {path}")]
    TlsCertParse { path: String },
    #[error("LND gRPC endpoint must include https:// scheme: {endpoint}")]
    MissingScheme { endpoint: String },
    #[error("invalid LND gRPC endpoint: {endpoint} ({source})")]
    InvalidEndpoint { endpoint: String, source: tonic::transport::Error },
    #[error("tonic TLS config failed: {0}")]
    TlsConfig(tonic::transport::Error),
    #[error("macaroon hex encoding produced invalid metadata value")]
    MacaroonInvalid,
}

impl LndGrpcClient {
    /// Validates endpoint shape, reads + parses the TLS cert,
    /// hex-encodes the macaroon. **Does not hit the network** (per
    /// ADR-C3 § C3.5). The channel is built with `.connect_lazy()`;
    /// the first RPC triggers the actual dial.
    pub fn new(
        endpoint: String,           // from LndNodeConnection.grpc_endpoint
        tls_cert_path: String,      // from LndNodeConnection.tls_cert_path
        macaroon: &SecretString,    // from LndNodeConnection.macaroon
        timeout: Duration,
    ) -> Result<Self, BuildError>;

    pub async fn get_info(&self) -> Result<GetInfoResponse, LndRpcError>;
    pub async fn list_channels(&self) -> Result<ListChannelsResponse, LndRpcError>;
    pub async fn list_peers(&self) -> Result<ListPeersResponse, LndRpcError>;
}

#[derive(Debug, thiserror::Error)]
pub enum LndRpcError {
    #[error("tonic status: code={0:?} message={1:?}")]
    Status(tonic::Code, String),
    #[error("transport error: {0}")]
    Transport(tonic::transport::Error),
    #[error("response decode failed: {0}")]
    Decode(#[from] prost::DecodeError),
    #[error("timeout after {0:?}")]
    Timeout(Duration),
}
```

`channel.clone()` is cheap in tonic (it's an `Arc` internally); per
RPC the client spawns a generated `LightningClient` from the cloned
channel, which is the idiomatic pattern.

**Startup-failure policy.** A missing or malformed TLS cert at
collector construction is a `BuildError`. This aborts sidecar
bootstrap rather than masking a config error as a perpetual runtime
failure — config bugs should be loud at startup. An LND node that
is briefly unreachable at startup is **not** a `BuildError`: the
endpoint URL is validated for shape and the channel is built
lazily, so first poll surfaces `ProbeResult::Failed` per ADR-C3
§ C3.5. (Same split as Bitcoin: bad RPC password = startup abort,
bitcoind temporarily down = first-poll failure.)

### E2.4 — `LndGrpcPollingCollector` shape

Mirrors `BitcoinCoreRpcCollector` (`src/collectors/bitcoin_core/rpc.rs`):

```rust
// src/collectors/lnd/grpc_poll.rs

use std::time::Duration;
use async_trait::async_trait;

use crate::collectors::lnd::grpc_client::{BuildError as ClientBuildError, LndGrpcClient};
use crate::collectors::registry::LndNodeConnection;  // NEW — see below
use crate::collectors::traits::PollingCollector;
use crate::collectors::{
    CollectionContext, CollectorDescriptor, CollectorTarget,
};
use crate::observations::ObservationBatch;
use crate::shared::types::LndNodeId;

#[derive(Debug, Clone)]
pub struct LndGrpcPollingCollectorConfig {
    pub timeout_per_rpc: Duration,
}

impl Default for LndGrpcPollingCollectorConfig {
    fn default() -> Self {
        Self { timeout_per_rpc: Duration::from_secs(5) }
    }
}

#[derive(Debug, thiserror::Error)]
pub enum BuildError {
    #[error("collector target must be LndNode, got {0:?}")]
    WrongTargetKind(CollectorTarget),
    #[error("client build failed: {0}")]
    Client(#[from] ClientBuildError),
}

pub struct LndGrpcPollingCollector {
    descriptor: CollectorDescriptor,
    node_id: LndNodeId,
    client: LndGrpcClient,
}

impl LndGrpcPollingCollector {
    /// Free constructor matching ADR-C3 § C3.2. The runtime
    /// hand-wires this from a CollectorDescriptor + the resolved
    /// connection details. No network call (ADR-C3 § C3.5).
    pub fn new(
        descriptor: CollectorDescriptor,
        connection: LndNodeConnection,
        config: LndGrpcPollingCollectorConfig,
    ) -> Result<Self, BuildError>;
}
```

`LndNodeConnection` **already exists** in
`src/collectors/registry.rs` with the shape:

```rust
pub struct LndNodeConnection {
    pub grpc_endpoint: String,
    pub rest_endpoint: Option<String>,    // ignored by V0.8 (REST deferred)
    pub macaroon: SecretString,           // resolved value, not a path
    pub tls_cert_path: String,
}
```

E2 does not migrate this struct. It uses the existing fields:
`grpc_endpoint` for the tonic channel, `tls_cert_path` for the cert
to load at construction, `macaroon` (the resolved `SecretString`)
hex-encoded into the request metadata. `rest_endpoint` is unused in
V0.8 — REST is deprecated upstream and there's no V0.8 rule that
needs it.

`impl PollingCollector for LndGrpcPollingCollector` mirrors the
Bitcoin shape: parallel RPCs via `tokio::join!`, deterministic
spec-order processing, partials preserved in `ProbeResult::Failed`
on any failure.

### E2.5 — V0.8 RPC surface

Three RPCs per poll tick (default 30s, configurable per
`IntegrationKind::LndGrpcPoll { interval }`). The service is
`lnrpc.Lightning`; the method names below use the unqualified form
for brevity.

| RPC | Response shape | Produces | Catalog rules served |
|---|---|---|---|
| `GetInfo` | `GetInfoResponse` | `StateObservation::LndNode(LndNodeState)` | B6 (chain-backend lag — reads `block_height`) |
| `ListChannels` | `ListChannelsResponse` | `StateObservation::LndChannelSummary(LndChannelSummaryState)` PLUS one `StateObservation::LndChannel(LndChannelState)` per channel (ADR-E1 § E1.1) | B1 (channel inactive — reads `.active`) |
| `ListPeers` | `ListPeersResponse` | Joined into per-channel observations (see below) | B1 enrichment |

**Why not `WalletBalance`?** It populates `LndWalletState` but no
V0.8 rule consumes wallet balances. Per ADR-C3's principle —
"smallest shape that gets a real collector running and matches the
catalog's V0 diagnostic needs" — adding RPCs for "future surface"
is scope creep. `WalletBalance` lands when a rule needs it (a
v0.x cold-wallet-balance-alert ticket, a v1.x channel-rebalance
rule, etc.), not before.

**ListPeers cross-reference.** ListPeers isn't emitted as its own
state observation in V0.8. Instead, the collector joins it into
`LndChannelState` at observation-build time: for each `Channel`
returned by `ListChannels`, look up the matching `Peer` by
`remote_pubkey` in the `ListPeers` response and stamp the result
into `LndChannelState.peer_online` (added to E1.1's struct
definition as part of this ADR landing — see the Spec updates
section).

**Partial-failure semantics for `peer_online`:**

- `Some(true)` — peer was connected during this poll
- `Some(false)` — peer was not connected during this poll
- `None` — the cross-reference could not be made (ListPeers RPC
  failed in this tick while ListChannels succeeded). The channel
  state is still emitted but lands in
  `ProbeResult::Failed.partial_observations` per the collector's
  partial-failure contract (mirrors Bitcoin's ADR-C3 pattern). The
  B1 rule should treat `None` as "no peer-online context this tick"
  and either skip the suspicious-vs-routine distinction or wait for
  the next tick.

Per ADR-C3 § C3.4, each successful RPC also emits a health
observation (see E2.10).

### E2.6 — TLS: trust the configured LND cert only

LND's TLS cert is self-signed by default. Trust must come from the
operator-configured cert file, not from native OS roots. This
matches what `lncli` does and prevents any compromised public CA
from MITM-ing the channel.

```rust
let pem = std::fs::read(&tls_cert_path)
    .map_err(|e| BuildError::TlsCertRead { path: tls_cert_path.clone(), source: e })?;

let ca = tonic::transport::Certificate::from_pem(&pem);
let tls = tonic::transport::ClientTlsConfig::new()
    .ca_certificate(ca);

let channel = tonic::transport::Channel::from_shared(endpoint.clone())
    .map_err(|e| BuildError::InvalidEndpoint { endpoint, source: e.into() })?
    .tls_config(tls)
    .map_err(BuildError::TlsConfig)?
    .connect_lazy();
```

`connect_lazy()` is critical for ADR-C3 § C3.5 — construction must
not hit the network. The first RPC triggers the actual dial.

**The `tls-roots` and `tls-webpki-roots` tonic features are NOT
enabled.** A future ADR can opt into native roots if a managed LND
deployment ever ships with a publicly-signed cert chain, but for
V0.8 the constraint is strict cert-pinning.

**SNI / domain_name override (operator awareness).** LND's
self-signed cert is typically issued for `localhost`. If the
operator dials by IP or a non-localhost hostname, TLS handshake
fails with an SNI mismatch. `tonic::transport::ClientTlsConfig::domain_name(...)`
overrides the expected SNI hostname. V0.8 does NOT expose this
knob in `[collectors.lnd]` config; the common deployment is
co-located sidecar+LND where `localhost` works. Operators dialing
across hosts hit this and need a small follow-on to add an
optional `[collectors.lnd.nodes.<id>].tls_domain_name` field.
Naming the gap here so the first cross-host deployment doesn't
fail mysteriously.

### E2.7 — Macaroon authentication: per-request metadata header

The macaroon is loaded from disk at collector construction, encoded
to lowercase hex, and attached to every outgoing request as the
`macaroon` metadata header. No tonic interceptor for V0.8.

```rust
async fn get_info(&self) -> Result<GetInfoResponse, LndRpcError> {
    let mut client = LightningClient::new(self.channel.clone());
    let mut request = tonic::Request::new(GetInfoRequest {});
    let mac_val: tonic::metadata::MetadataValue<_> = self
        .macaroon_hex
        .parse()
        .map_err(|_| LndRpcError::MacaroonInvalid)?;
    request.metadata_mut().insert("macaroon", mac_val);

    let outcome = tokio::time::timeout(self.timeout, client.get_info(request)).await;
    match outcome {
        Err(_) => Err(LndRpcError::Timeout(self.timeout)),
        Ok(Err(status)) => Err(LndRpcError::Status(status.code(), status.message().into())),
        Ok(Ok(response)) => Ok(response.into_inner()),
    }
}
```

Per-request rather than per-channel because LND's gRPC server
expects the header on every call. No interceptor because macaroons
don't expire mid-poll for V0.8's read-only surface; the simpler
shape is the right shape until rotation or per-RPC capability
constraints land.

### E2.8 — Per-RPC timeout

Each RPC wrapped in `tokio::time::timeout(self.timeout, ...)`, with
`self.timeout` from `LndGrpcPollingCollectorConfig.timeout_per_rpc`
(default 5 seconds). Matches ADR-C3 § C3.7. The poll's worst-case
wall time is one timeout window since the four RPCs run in parallel
via `tokio::join!`.

Inner `tonic::Code::DeadlineExceeded` and outer
`tokio::time::error::Elapsed` are mapped identically to
`CollectionErrorKind::Timeout`. The outer timeout is what the
collector actually relies on; gRPC's deadline is informational
overlap.

### E2.9 — Error mapping: `tonic::Status` → `CollectionErrorKind`

Extends ADR-C3 § C3.8's table:

| Source | `CollectionErrorKind` |
|---|---|
| `tonic::Code::Unavailable` (server down, network) | `Unreachable` |
| `tonic::Code::DeadlineExceeded` (server-side deadline) | `Timeout` |
| `tokio::time::timeout` (our outer wrapper) | `Timeout` |
| `tonic::Code::Unauthenticated` (missing / invalid macaroon) | `AuthenticationFailed` |
| `tonic::Code::PermissionDenied` (macaroon valid, lacks capability) | `PermissionDenied` |
| `tonic::Code::FailedPrecondition` (wallet locked, LND not synced, etc.) | `Misconfigured` |
| `tonic::Code::Internal` (LND internal error) | `Internal` |
| `tonic::Code::Unimplemented` (LND version missing the RPC) | `UnsupportedVersion` |
| `tonic::Code::ResourceExhausted` (rate limited) | `RateLimited` |
| TLS handshake failure | `Unreachable` |
| `tonic::Code::InvalidArgument` (bad request payload) | `InvalidResponse` |
| Decode failure (prost decode error) | `DecodeError` |
| Invalid macaroon hex (parse failure at construction) | `Misconfigured` |

`LndRpcError → CollectionErrorKind` mapping happens at the collector
boundary, the same shape as Bitcoin's pattern in ADR-C3 § C3.8.

### E2.10 — Health observations per RPC

Per ADR-C3 § C3.4: every successful RPC emits a
`HealthCheckObservation` with target `lnd.rpc.<method>` and latency
stamped:

- `lnd.rpc.get_info`
- `lnd.rpc.list_channels`
- `lnd.rpc.list_peers`

On RPC failure, the same target is emitted with
`HealthStatus::Critical` and a `HealthError` carrying the kind from
the table in E2.9. Operators can alert on per-RPC degradation
(e.g. `list_channels` failing while the other three succeed often
signals a corrupt LND channel.db).

**Rationale.**

- **Mirror the Bitcoin pattern, don't invent.** ADR-C3 already
  decided the polling-collector shape (descriptor + node_id +
  thin client + parallel RPCs + health observations). Following
  that pattern keeps the codebase coherent and minimizes the
  cognitive load of "two ways to write a collector."
- **Vendor LND's protos at a pinned version.** LND publishes
  authoritative `.proto` files; vendoring them gives build
  determinism and removes the third-party-crate-maintenance risk
  for a moving target. The cost is one README and a
  review-on-LND-release habit.
- **Tonic with `tls` only, no native roots.** LND ops uses
  self-signed certs as the default; trusting public CAs adds
  no value and adds a MITM-via-compromised-CA risk. `lncli` does
  the same pinning; consistency with the LND ecosystem norm.
- **Per-request macaroon header, no interceptor.** Macaroons don't
  rotate mid-poll for V0.8's read-only surface. Interceptor pattern
  has its place when capabilities, rotation, or per-call constraints
  matter; V0.8 has none of those.
- **One `tonic::Channel` per LND node.** TLS roots and macaroons are
  per-node; sharing a channel would require multiplexing trust
  contexts at the channel layer, which tonic doesn't support and
  which would be a security smell anyway.
- **ListPeers as cross-reference into LndChannelState, not its own
  state variant.** Per-peer state surface isn't consumed by any
  v0.8 rule; introducing a state variant for it would inflate the
  state vocabulary without consumer. The `peer_online: Option<bool>`
  field on `LndChannelState` covers B1's enrichment need with
  minimum new surface.

**Alternatives considered.**

- **Use a published Rust crate for LND types** (e.g.
  `lnd-grpc-tonic-client`). Rejected per E2.2 — third-party crates
  for moving-target APIs become maintenance liabilities; vendoring
  the protos directly is simpler and gives us version control.
- **Enable `tonic`'s `tls-roots` or `tls-webpki-roots` feature.**
  Rejected per E2.6 — native roots aren't useful for a self-signed
  cert deployment and introduce CA-compromise risk.
- **Tonic interceptor for macaroon header.** Rejected for V0.8 per
  E2.7 — adds indirection for no current benefit. Revisit when
  macaroon rotation, per-RPC capability checks, or auth-token
  refresh actually lands.
- **Per-LND-node shared `tonic::Channel` via multiplexing.**
  Rejected per "TLS roots are per-node" — not supportable in tonic,
  also a security smell.
- **Emit per-peer state observations via a new `LndPeerState`
  variant.** Rejected for V0.8 — no rule consumes per-peer state;
  the cross-reference into `LndChannelState.peer_online` covers
  B1's enrichment without growing the state vocabulary.
- **Drop `ListPeers` from V0.8 entirely** to keep the RPC surface
  minimal. Rejected because B1's accuracy meaningfully improves
  with peer-online context (distinguishes "peer offline → channel
  inactive" routine case from "peer online → channel inactive"
  suspicious case), and the cost is one extra RPC per 30s.
- **REST API instead of gRPC.** Rejected — LND's REST is deprecated
  and lacks coverage of newer subscription endpoints (relevant for
  v1.0). Going straight to gRPC avoids a forced migration later.
- **Hand-roll the gRPC envelope** (no tonic-build, no prost).
  Rejected — gRPC is more complex than JSON-RPC; the
  prost+tonic-build path is the well-trodden default, and the
  build-script overhead is tiny.
- **Include `WalletBalance` in V0.8 for future surface.** Rejected
  per E2.5 — adding RPCs without consumer rules violates ADR-C3's
  "smallest shape that gets a real collector running" principle.
  `WalletBalance` lands with a real rule consumer, not before.

**Spec updates queued.**

- § 7.3 — flesh out `LndGrpcPollingCollector` struct + run loop.
- § 7.4 — `LndNodeConnection` (already in `registry.rs`) is the
  source of truth for LND connection parameters; no new struct.
- § 7.5 — add `LndRpcError` and the `tonic::Status →
  CollectionErrorKind` table.
- § 7.6 — note that LND uses a per-node `tonic::Channel`, not the
  shared `reqwest::Client` pattern.
- § 7.7 — replace "LND collectors: none" with the V0.8
  `LndGrpcPollingCollector`.
- § 21.3 / § 21.6 — refresh trait + collector inventory to include
  the LND polling impl.
- **Amends ADR-E1 § E1.1** — `LndChannelState` gains a
  `peer_online: Option<bool>` field. The field is added directly to
  E1.1's struct definition (landing in the same commit as this ADR)
  rather than left to implementation, so future readers of E1
  alone get the correct shape.

**Open follow-ons (do not block v0.8 tickets).**

- **ADR-E3 — LND subscription patterns** (v1.0). Stream reconnect +
  reconcile contract for `SubscribeChannelEvents`,
  `SubscribeHtlcEvents`, etc. Out of scope for v0.8.
- **ADR-D5 / ADR-E4 — Smart-constructor migration for LND
  identifiers.** Deferred per ADR-E1 § E1.6. Per-type parsers
  (66-char hex for pubkeys, SCID grammar for channel IDs, etc.).
- **Tonic interceptor for macaroon auth.** Lands when macaroon
  rotation, per-RPC capability checks, or refresh tokens become
  real requirements.
- **Macaroon constraint validation.** LND macaroons can carry
  caveats (time, IP, capability). V0.8 trusts the operator's
  configured macaroon as-is; future ADR can add caveat-aware
  construction for least-privilege deployment patterns.
- **Proto file vendoring policy.** A small follow-on documents the
  review-on-LND-release cadence and which sub-services (signrpc,
  walletrpc, watchtower-as-server) get vendored when.
