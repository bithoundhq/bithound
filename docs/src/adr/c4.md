# ADR-C4 — ZMQ subscription collector

**Date.** 2026-05-23.
**Status.** Deferred (originally proposed 2026-05-23; deferred same day
when V1 scope pivoted to LND-first — see project design doc).
**Scope.** The implementation contract for `BitcoinCoreZmqCollector` —
the first concrete `SubscriptionCollector` (per ADR-C1). Originally
planned as the load-bearing piece of v0.8; now planned to land in
v1.0 alongside LND subscription streams (ADR-E3).

**Deferral rationale.** V0.8 was originally scoped as a ZMQ-first
Bitcoin Core wedge. On re-examination it became clear that ZMQ
improves Bitcoin Core detection latency (10s → 1s) but doesn't unlock
new incident categories — reorg, mempool burst, and tip-lag are all
detectable via RPC polling at degraded latency. Meanwhile, LND
observability is a genuine ecosystem gap with no good off-the-shelf
tooling. V1 was re-cut as LND-first (v0.8 polling, v1.0 subscriptions
+ ZMQ). This ADR's contract is unchanged; only the scheduling moved.
When ZMQ work begins in v1.0, this ADR moves back to Proposed for a
final review, then Accepted.

**Context.** ADR-C1 defined the `SubscriptionCollector` trait but
deferred all subscription implementations to "V0.1+." ADR-C3 § C3.3
stubbed `src/collectors/bitcoin_core/zmq.rs` and § C3.2 named
`IntegrationKind::BitcoinCoreZmq` (`src/collectors/types.rs:60`). V0
shipped without a concrete subscription collector; the runtime can
spawn one, but nothing implements it.

v0.8's wedge — real-time reorg detection, real-time tip-lag,
mempool-burst classification — depends on observations that polling
exporters structurally cannot surface. ZMQ is the only protocol-native
way to get block-arrival and mempool-delta events with low latency. This
ADR locks the implementation contract before any v0.8 ticket lands.

Four questions the design must answer:

1. **Backpressure** when consumer falls behind a ZMQ event burst.
2. **Sequencing** across the three independent ZMQ sockets.
3. **Reconnect + catch-up** when the ZMQ connection drops.
4. **Heartbeat** distinguishing "chain quiet" from "ZMQ silently dead."

Plus three follow-ons that emerge once those four are answered:

5. The collector's `Err` boundary (when does it return up to the runtime).
6. Observation payload mapping (which existing variants, which new).
7. Config surface and `CollectionError` mapping.

**Decision.**

### C4.1 — Backpressure: `drop_oldest` with explicit telemetry

The `BatchSink` channel from ADR-C1 wraps a bounded
`mpsc::Sender<ObservationBatch>`. Under burst (block-storm, fee-spike,
or stalled consumer), the collector cannot afford to block its own
read loop: Bitcoin Core's ZMQ socket has no replay, so any event the
collector fails to read off the socket promptly is lost forever.

V0.8 policy is **`drop_oldest`** at the collector level, with explicit
telemetry:

- Internal staging is a small `tokio::sync::mpsc::channel(64)` between
  the per-socket ZMQ readers and the batch-assembly task. When this
  channel is full, the reader uses `try_send` and on `Full` increments
  a `dropped_events_total` counter and continues. Never block the
  reader.
- On every dropped event, emit a `bithound.observation_dropped`
  observation (see ADR-?? Operability — to land alongside ADR-C4)
  carrying the topic (`hashblock` | `sequence`), drop count since
  last report, and the ZMQ sequence cursor at drop time.
- The outer `BatchSink` (collector → consumer) keeps its bounded
  channel and *does* exert backpressure on the batch-assembly task —
  that is fine, because the assembly task can wait without losing
  events from the ZMQ socket itself.

This makes drop explicit and observable rather than silent. A live
incident counter on dropped ZMQ events is itself a `bithound.*`
diagnostic surface — operators see Bithound losing fidelity before it
manifests as missed Bitcoin incidents.

### C4.2 — Three sockets, `sequence` is the canonical spine

Bitcoin Core's ZMQ surface exposes independent SUB sockets per topic.
v0.8 subscribes to **two** of the three documented topics:

- **`hashblock`** — block hash announcements on connect. Used for
  real-time tip changes and as the trigger for RPC enrichment
  (`getblockheader`).
- **`sequence`** (Bitcoin Core 0.21+) — ordered events:
  - `A:<txid>` — mempool accept
  - `R:<txid>` — mempool remove
  - `C:<hash>` — block connect (with mempool sequence)
  - `D:<hash>` — block disconnect

  `sequence` is the canonical timeline. Anything joined from another
  socket joins by hash to a `sequence` event. There is no idle
  heartbeat tick (this surprised the author; see C4.4).

**Deferred:** `rawtx` is **not** subscribed in v0.8. Mempool acceptance
rate is derivable from `sequence` `A:` / `R:` counts; per-tx bodies are
not consumed by any v0.8 rule and would impose 1-100 obs/sec storage
pressure for no rule value. Revisit in v1.1+ when a rule actually
needs tx-level detail (RBF feature, large-fee-anomaly, etc.).

The collector spawns one tokio task per subscribed socket. Each task
reads frames and forwards `(topic, payload, zmq_sequence)` tuples to
the batch-assembly task. Assembly joins `hashblock` + `sequence` `C:`
events by hash to produce coherent block-connect observations.

If `hashblock` arrives before its `sequence` `C:` counterpart (race
condition), assembly buffers the hash with a short timeout (default
500ms). If `sequence` `C:` never arrives, the buffered hash is
discarded and a `bithound.zmq_join_timeout` observation is emitted.

### C4.3 — Reconnect: exponential backoff + RPC catch-up gap-fill

ZMQ subscriptions can die transiently (bitcoind restart, network
flap, OS socket churn). The collector handles all transient
reconnects **internally** without returning to the runtime — the
runtime's supervisor restart is reserved for terminal failure (see
C4.5).

Reconnect policy:

- **Backoff:** 1s → 2s → 4s → 8s → 16s → 30s, with ±20% jitter; caps
  at 30s. Configurable via `reconnect_backoff_max`.
- **Outer budget:** total reconnect-retry time is bounded at 1 hour
  by default. Exhausting the budget returns
  `Err(CollectionError { kind: Unreachable, … })` to the runtime,
  which then re-spawns per ADR-C1.

**Gap-fill via RPC**: after a successful reconnect, the collector
must reconcile the gap between the last-observed block hash and the
current bitcoind tip:

1. Read last-observed tip hash from the collector's local state.
2. Use the shared `BitcoinRpcClient` (per ADR-C3 § C3.6 — already
   constructed for the RPC collector) to call `getblockhash N` from
   `last_observed_height + 1` to `current_tip_height`, then
   `getblockheader hash` to get prev-hash links.
3. Emit synthetic `StateObservation::BitcoinBlockchainState` updates
   *and* (if a reorg is detected during gap-fill — see C4.6)
   `ChainReorgObservation`s. Stamp them with
   `ObservationOrigin::Computed` so rules can tell catch-up from live.
4. Resume subscription emission once `local_tip == bitcoind_tip`.

If the RPC client is itself unreachable during gap-fill, the collector
treats this as a transient failure (retry the reconnect cycle from
step 1). A persistent RPC outage during catch-up will hit the outer
budget and surface as `Unreachable` to the runtime — operationally
indistinguishable from "bitcoind is down," which is the truth.

### C4.4 — Liveness via cross-collector reconciliation, not traffic absence

Bitcoin Core's `pubsequence` topic publishes only on real events
(block connect/disconnect, mempool accept/remove). There is no idle
heartbeat tick. On mainnet, continuous mempool activity makes
`sequence` effectively never idle (1-10 events/sec under normal load),
so "no traffic for N seconds" would look like a viable liveness
signal. But on testnet, signet, regtest, during IBD, or while the
node has zero peers, "no `sequence` traffic for N seconds" is a
normal state. A traffic-absence heartbeat would false-positive on
every non-mainnet network and on every quiet mainnet edge case.

The ZMQ collector instead uses **cross-collector reconciliation**
against the existing polling collector as its liveness signal.

A shared `Arc<RwLock<ObservedChainTip>>` is constructed once per
Bitcoin node and handed to both the `BitcoinCoreRpcCollector` and
the `BitcoinCoreZmqCollector` during the runtime hand-wiring step
(ADR-C3 § C3.2). The cursor stores:

```rust
struct ObservedChainTip {
    rpc_tip: Option<(BlockHash, u64, DateTime<Utc>)>,  // hash, height, observed_at
    zmq_tip: Option<(BlockHash, u64, DateTime<Utc>)>,
}
```

Each collector updates its own field: the RPC collector on every
successful `getblockchaininfo`, the ZMQ collector on every `hashblock`
arrival or `sequence` `C:` event. Neither collector reads the other's
field except via the reconciliation tick.

A reconciliation tick inside the ZMQ collector runs every
`reconcile_interval` (default `15s`) and checks:

- If `rpc_tip.height > zmq_tip.height` (or `zmq_tip == None` after
  the first successful RPC poll)
- AND `rpc_tip.observed_at − zmq_tip.observed_at > zmq_lag_threshold`
  (default `30s`)

then ZMQ has silently missed events. The collector emits a
`bithound.zmq_silently_dead` observation, closes both sockets, and
enters the C4.3 reconnect flow as if the connection had dropped.

Worst-case detection latency:
`rpc_interval + reconcile_interval + zmq_lag_threshold` ≈ **55s**
(10s + 15s + 30s) at defaults. Better than the 90s
traffic-absence design and works on every network.

This catches the real failure mode — Bitcoin Core's ZMQ pub queue
silently stuck while the daemon itself is fine, a documented
historical bug class. The case where both RPC and ZMQ are dead is
already covered by `BitcoinRpcUnreachableRule`; ZMQ liveness here is
specifically about the "RPC works, ZMQ silently doesn't" gap.

### C4.5 — `Err` boundary: transient handled internally, terminal returns

Per ADR-C1, the runtime decides whether to re-spawn a
`SubscriptionCollector` on `Err`. To avoid process-restart loops on
ordinary network blips, the collector handles all transient failures
internally (C4.3 reconnect, C4.4 silently-dead recovery) and returns
`Err(CollectionError)` only on:

- **Reconnect-budget exhaustion** (1 hour of continuous reconnect
  failure) → `CollectionErrorKind::Unreachable`.
- **Authentication / config failure** during connect (e.g. wrong
  endpoint, unsupported ZMQ topic on remote node) →
  `Misconfigured` (not retryable) — runtime should surface but
  not re-spawn on a 1-second loop.
- **Sink closed** by the runtime → `Internal` with a "sink closed"
  message; the runtime is shutting down anyway, so this is
  informational.

Inside the collector, transient ZMQ errors are folded into health
observations (`bithound.zmq_reconnect`, `bithound.zmq_disconnected`)
rather than propagated. This keeps the collector's `Err` channel
reserved for "the supervisor needs to do something different."

### C4.6 — Observation payload mapping

ZMQ event → `ObservationPayload` variant:

| ZMQ event | Maps to | Variant in `ObservationPayload` |
|---|---|---|
| `hashblock` (+ `getblockheader` RPC enrichment) | Updated chain tip | `State(BitcoinBlockchainState)` — existing |
| `sequence` `C:<hash>` (block connect) | Same as above | `State(BitcoinBlockchainState)` — existing |
| `sequence` `D:<hash>` (block disconnect) followed by `C:` of a different hash | Reorg event | **`ChainReorg(ChainReorgObservation)` — NEW** |
| `sequence` `A:<txid>` / `R:<txid>` aggregated in a tumbling window | Mempool accept/remove rate | `Metric(MetricObservation)` — existing (`bitcoin.mempool.accept_rate`, `bitcoin.mempool.remove_rate`) |
| Reconciliation tick (C4.4) detects ZMQ behind RPC | ZMQ silently dead | `Health(HealthCheckObservation)` with target `bithound.zmq_silently_dead` |
| Internal events (drop, reconnect, join timeout, silently-dead) | Bithound self-observability | `Health(HealthCheckObservation)` with target `bithound.*` — existing |

**One new payload variant** lands in this ADR:

```rust
// src/observations/types/chain_reorg.rs (NEW)
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ChainReorgObservation {
    /// The hash of the block where the reorg branched (last common ancestor).
    pub fork_hash: BlockHash,
    /// The height of the fork point.
    pub fork_height: u64,
    /// Hashes of blocks that were on the old chain but no longer are.
    /// Ordered from fork+1 to (old) tip.
    pub orphaned: Vec<BlockHash>,
    /// Hashes of blocks that are now on the chain. Ordered from fork+1
    /// to (new) tip.
    pub adopted: Vec<BlockHash>,
    /// Depth = orphaned.len() (same as adopted.len() except in very
    /// rare equal-work cases). Convenience for severity gating.
    pub depth: u32,
}
```

Folded into `ObservationPayload`:

```rust
pub enum ObservationPayload {
    Capability(CapabilityObservation),
    ChainReorg(ChainReorgObservation),                // NEW
    Diagnosis(DiagnosisObservation),
    Event(EventObservation),
    Heartbeat(HeartbeatObservation),
    Health(HealthCheckObservation),
    IncidentSignal(IncidentSignalObservation),
    Inventory(InventoryObservation),
    Metric(MetricObservation),
    State(StateObservation),
    Transition(TransitionObservation),
}
```

A constructor helper (`Observation::chain_reorg(ctx, …)`) is added
alongside the existing eleven, matching the ADR-R2 pattern.

`bitcoin.reorg_small` (1-2 depth) and `bitcoin.reorg_deep` (3+ depth)
rules consume `ObservationPayload::ChainReorg` directly — no string
parsing, no body deserialization. This is what "type-safety" buys.

### C4.7 — Config surface and `CollectionError` mapping

Config (per ADR-X1, `[collectors.bitcoin_core.zmq]`):

```toml
[collectors.bitcoin_core.zmq]
enabled = false                                  # default off
endpoints = { hashblock = "tcp://127.0.0.1:28332",
               sequence  = "tcp://127.0.0.1:28333" }
reconnect_backoff_initial = "1s"
reconnect_backoff_max     = "30s"
reconnect_budget          = "1h"                 # outer cap before Err to runtime
reconcile_interval        = "15s"                # cross-collector tick (C4.4)
zmq_lag_threshold         = "30s"                # max acceptable RPC-ahead-of-ZMQ lag
join_buffer_timeout       = "500ms"
internal_staging_capacity = 64
```

Env-var overrides per ADR-X1
(`BITHOUND_COLLECTORS_BITCOIN_CORE_ZMQ_ENABLED=true`, etc.).

`CollectionError` mapping for ZMQ-specific failures (extends the table
in ADR-C3 § C3.8):

| Failure | `CollectionErrorKind` |
|---|---|
| Endpoint connect refused | `Unreachable` |
| Topic unsupported by remote (`sequence` not enabled in bitcoind) | `UnsupportedVersion` |
| Reconnect budget exhausted | `Unreachable` |
| ZMQ frame decode error | `DecodeError` |
| RPC catch-up failure during reconcile | `Unreachable` (collector retries via reconnect cycle) |
| Sink closed | `Internal` |

**Rationale.**

- **Drop-oldest is honest, block-the-reader is silent.** Blocking the
  ZMQ read loop loses events the socket no longer offers; dropping in
  the staging channel loses events Bithound can name, count, and emit
  as a Bithound-self incident. The latter respects the append-only
  fact contract more cleanly than the former.
- **`sequence` as spine matches Bitcoin Core's own internal model.**
  The `sequence` topic was added in 0.21 precisely because the other
  topics aren't individually ordered. Treating it as canonical and
  joining others to it is the minimum-surprise choice.
- **Internal reconnect, runtime-Err for terminal.** Returning `Err`
  on every network blip would create a re-spawn loop, lose collector
  state, and treat ordinary failure modes as exceptional. The 1-hour
  budget puts terminal failure squarely in "operator-actionable"
  territory.
- **Cross-collector reconciliation, not traffic-absence heartbeat.**
  ZMQ topics don't emit idle ticks; a traffic-absence heuristic
  false-positives on every non-mainnet chain and on mainnet IBD /
  zero-peer / mempool-cleared edge cases. Reading the RPC collector's
  tip as ground-truth is the only network-agnostic signal, and reuses
  infrastructure that already exists.
- **One new payload variant, not three.** Reorgs are structurally
  distinct and rule-consumable; mempool deltas are rate metrics;
  block updates are real-time State refreshes. Adding three variants
  would bloat the type tree without rule-side payoff.
- **No `rawtx` in v0.8.** Per-tx bodies cost 1-100 observations/sec
  for no v0.8 rule. Deferring is reversible; subscribing too early
  forces premature storage and payload-variant decisions.

**Alternatives considered.**

- **Backpressure: `block` the reader.** Rejected per C4.1. ZMQ has
  no replay; blocked reads lose data silently. Drop-oldest with
  telemetry is the auditable shape.
- **Backpressure: spill-to-disk staging.** Rejected for V0.8 scope.
  Disk-backed queues are V2-tier complexity (file rotation, recovery
  on restart, integrity checks). Drop-oldest is the right V0.8 trade.
- **Subscribe to `rawtx` for completeness.** Rejected: no V0.8 rule
  consumes per-tx detail; the storage and observation-emit cost is
  100-1000× the value. Revisit when a real rule needs it.
- **One ZMQ task instead of one-per-socket.** Rejected: ZMQ SUB
  sockets aren't multiplexable through a single `recv` loop without
  losing the per-socket fairness `tokio::select!` provides; per-socket
  tasks make the timeout and backpressure semantics simpler.
- **Return `Err` on every ZMQ disconnect.** Rejected per C4.5.
  Triggers re-spawn loops on routine network blips and loses
  in-collector reconnect-budget bookkeeping.
- **Traffic-absence as liveness signal** (e.g. "no `sequence`
  messages for 90s means ZMQ is dead"). Rejected per C4.4. Works
  only on mainnet outside of IBD / zero-peer / cleared-mempool
  states; false-positives on every other chain. Cross-collector
  reconciliation is network-agnostic.
- **Verify ZMQ liveness via the consumer task instead of inside the
  collector.** Rejected: would couple `src/runtime/consumer.rs` to
  cross-collector reconciliation logic, breaking the consumer's
  single responsibility (apply observations → emit signals). The
  ZMQ collector owning its own liveness check keeps the consumer
  clean.
- **Add `MempoolTxObservation` typed variant up-front.** Rejected
  because no V0.8 rule consumes per-tx bodies; type variants should
  earn their place by serving at least one rule.
- **Add `BlockConnectObservation` separately from
  `BitcoinBlockchainState`.** Rejected: a connect *is* a chain-state
  update; treating it as a distinct payload type splits the rule
  surface (now reorg rules need to consume two variants instead of
  the existing state + the new reorg). State + ChainReorg is the
  minimal partition.
